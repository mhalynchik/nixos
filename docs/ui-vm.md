# Стенд для проверки рабочего стола

Профиль `nixosConfigurations.ui-test` запускает отдельную NixOS VM с модулями
Hyprland, Home Manager, Stylix, Waybar, AGS и Rofi из этого проекта.
Команда `bin/ui-vm` позволяет человеку или агенту собирать систему, видеть её
экран, нажимать клавиши, кликать мышью и выполнять команды внутри гостя.
Применять конфигурацию к основной системе для этого не требуется.

## Требования и запуск

Нужны Linux x86_64, Nix с flakes, Python 3, `ssh`, `ssh-keygen` и доступ пользователя
к `/dev/kvm` и `/dev/dri/renderD*` с работающим EGL/OpenGL. QEMU и зависимости VM предоставляет сборка Nix. На VM выделены
4 ядра, 4 GiB RAM и разреженный диск до 16 GiB. Первый запуск может скачивать
пакеты; следующие сборки используют Nix store и кеш.

Из корня репозитория:

```bash
bin/ui-vm start
bin/ui-vm wait
bin/ui-vm screenshot
bin/ui-vm smoke
bin/ui-vm stop
```

`start` сначала собирает текущие файлы проекта и затем запускает QEMU в фоне.
`wait` ждёт Hyprland, Waybar и AGS; таймаут задаётся через `--timeout 180`.
`screenshot` печатает абсолютный путь к PNG, который агент может открыть
инструментом просмотра изображений.

Для просмотра VM в отдельном окне используйте `bin/ui-vm start --window`
из графической сессии хоста. По умолчанию используется EGL без видимого окна.

Отдельная сборка и запуск уже собранного результата:

```bash
bin/ui-vm build
bin/ui-vm start --no-build
```

Сборка использует `path:` и `--no-write-lock-file`: новые файлы доступны Nix
без `git add`, а `flake.lock` не обновляется. Команды не выполняют deploy,
`nixos-rebuild switch`, коммиты или push.

## Управление интерфейсом

```bash
bin/ui-vm key super-enter
bin/ui-vm type 'Привет из VM' --paste-key ctrl-shift-v
bin/ui-vm key super-w
bin/ui-vm type 'kitty'
bin/ui-vm key esc
bin/ui-vm move 640 400
bin/ui-vm click 640 400
bin/ui-vm click 640 400 --button right
bin/ui-vm screenshot /home/USER/.local/share/agent-workspaces/ui-preview.png
```

Координаты — пиксели последнего экрана, от верхнего левого угла. Разрешение
профиля — 1280×800. `key` принимает QEMU qcodes, соединённые дефисом;
`super`, `enter`, `escape` также поддерживаются. `type` помещает UTF-8 текст
в буфер гостя и нажимает Ctrl+V; для терминала нужен Ctrl+Shift+V.

Команды выполняются от тестового пользователя `ui`; `ui-session` подставляет
окружение его графической сессии:

```bash
bin/ui-vm exec -- ui-session hyprctl clients -j
bin/ui-vm exec -- ui-session hyprctl configerrors
bin/ui-vm exec -- ui-session ags -t calendar-popup
bin/ui-vm exec -- journalctl --user -b -u waybar -u ags --no-pager -n 80
bin/ui-vm exec -- sudo journalctl -b -u greetd --no-pager -n 80
```

Для конвейеров используйте `exec -- bash -lc 'команда | другая команда'`.
Обычные аргументы экранируются перед отправкой через SSH.

## Цикл разработки

Этот порядок обязателен для агентов и участников проекта после реализации
новой функции или исправления поведения. Успешные Nix eval/build и общий
`smoke` сами по себе не подтверждают работу новой функции.

### 1. Определить проверяемое поведение

До изменений запишите краткие критерии результата в рабочем плане задачи:
действие пользователя или событие, ожидаемый результат и способ наблюдения.
Для исправления ошибки сначала воспроизведите её, если это возможно.

Выберите сценарии по смыслу изменения:

- Основной путь: открыть новую панель, выполнить действие, увидеть результат.
- Отмена или ошибка: Escape, неверный ввод, недоступная служба либо устройство.
- Повторный вызов: повторное открытие, закрытие, повтор действия без дубликатов.
- Сохранение состояния: перезапуск приложения/службы или загрузка новой сборки.
- Соседние функции: общие хоткеи, popup, буфер обмена, звук, блокировка.

Убедитесь, что функция **включена в тестовой конфигурации**. По умолчанию
необязательные приложения и большинство `features` выключены. Для них
используйте [отдельный профиль проверки](#профиль-для-новой-функции-или-темы).
Не подменяйте проверяемую реализацию заглушкой ради прохождения теста.

### 2. Собрать текущие исходники и запустить VM

Все команды выполняются из корня проекта. Для отдельной задачи удобно
выделить собственный каталог состояния. Сохраните значение `UI_VM_STATE`
и передавайте его в каждый новый терминал, включая запуск Python-тестов.

```bash
export UI_VM_STATE="$HOME/.local/share/agent-workspaces/ui-feature"
bin/ui-vm paths
mkdir -p "$UI_VM_STATE/evidence"
```

Сначала вызывается `paths`: он создаёт маркер стенда. Не создавайте файлы,
логи и ссылку `build` внутри нового каталога состояния до этого вызова —
защита инструмента отвергнет непустой каталог без маркера.

Одновременно может работать только одна VM на порту 22222, даже с разными
каталогами состояния. Не останавливайте VM другой задачи. Убедитесь, что
порт свободен или что работает именно ваш стенд.

Для стандартного профиля выполните следующий блок; при ошибке он остановится:

```bash
(
  set -e
  bin/ui-vm stop
  bin/ui-vm build > "$UI_VM_STATE/evidence/build.log" 2>&1
  bin/ui-vm start --no-build
  bin/ui-vm wait --timeout 180
  bin/ui-vm exec -- hostname
  bin/ui-vm smoke > "$UI_VM_STATE/evidence/smoke.log" 2>&1
)
```

Ожидаемый hostname — `ui-test`. При неуспешной команде прочитайте её лог,
исправьте причину и повторите соответствующий шаг. После изменения исходников
нужна новая сборка; запуск старого результата с `--no-build` не проверяет правку.
Для собственного профиля замените шаг `build` командой из раздела ниже.

### 3. Проверить именно новую функцию

Запустите пользовательский сценарий через реальные клавиши/клики, дождитесь
наблюдаемого результата и откройте снимок экрана инструментом просмотра.
Само создание PNG или наличие процесса не доказывает корректность интерфейса.
Проверьте текст, цвета, размеры, фокус, закрытие окна и результат действия.

```bash
bin/ui-vm screenshot "$UI_VM_STATE/evidence/before.png"
bin/ui-vm key super-enter
bin/ui-vm exec -- ui-session hyprctl clients -j
bin/ui-vm screenshot "$UI_VM_STATE/evidence/after.png"
bin/ui-vm exec -- ui-session hyprctl configerrors
bin/ui-vm exec -- systemctl --failed --no-pager
bin/ui-vm exec -- systemctl --user --failed --no-pager
```

Это пример открытия терминала: замените действие на реальный сценарий своей
функции. Для фоновой службы проверяйте её состояние, журнал и фактический
результат работы. Для приложения, открываемого напрямую, используйте
`bin/ui-vm exec -- ui-session hyprctl dispatch exec 'команда-приложения'`.
Журналы изменённой службы сохраните через команды из раздела управления.

При изменениях конфигурации, активации Home Manager или тем проверьте два
случая: первую загрузку с чистым профилем и обновление с сохранённым диском.
Для чистой проверки используйте новый каталог `UI_VM_STATE`, предварительно
остановив предыдущую VM. Для обновления оставьте тот же каталог и диск,
соберите изменённый профиль и перезапустите стенд. При смене тем проверяйте
также возврат к исходной теме. Это выявляет старый CSS, оставшиеся настройки
и ошибки миграции, которые не видны на чистой системе.

### 4. Выполнить подходящие регрессионные проверки

Выберите тесты по изменённому поведению из списка ниже. При изменениях общих
компонентов рабочего стола запустите весь `tests/desktop_vm.py`; для локальной
правки достаточно относящихся к ней сценариев. Например, для блокировки:

```bash
python3 tests/desktop_vm.py \
  DesktopRegressions.test_idle_daemon_receives_lock_request \
  DesktopRegressions.test_idle_timer_locks_session
```

Для новой логики, не покрытой существующими проверками, добавьте подходящий
регрессионный тест. Графические сценарии размещайте в `tests/`, используя
транспорт из `bin/ui-vm` и примеры `tests/desktop_vm.py` / `tests/theme_vm.py`.
Сохраняйте проверку hostname `ui-test`, ждите конкретное состояние с таймаутом
и убирайте временные окна/данные. Тесты, посылающие ввод, запускаются строго
последовательно. Нельзя одновременно выполнять `smoke`, другой UI-тест
или вручную управлять той же VM.

После правок выполняйте `git diff --check`; перед передачей результата —
`agent-check "$PWD"`. Это дополнительные проверки, они не заменяют VM.

### 5. Зафиксировать результат и остановить стенд

Сохраняйте снимки, журналы и заметки вне репозитория, например в
`$UI_VM_STATE/evidence`. Используйте отдельные имена или подкаталоги для
разных тем/версий, чтобы следующая проверка не затёрла доказательства предыдущей.
В репозитории остаются исходники, повторяемые тесты
и документация. Не создавайте для этой процедуры `AGENTS.md`, `.codex/`
или другие файлы настройки агента; не выполняйте `git add`, commit или push.

В итоговом сообщении укажите:

- Какие файлы и поведение изменились.
- Какой профиль/тема/приложение проверены; диск был чистым или сохранялся.
- Какие действия выполнены, что наблюдалось, какие команды и тесты прошли.
- Ссылки на снимки и относящиеся к изменению журналы.
- Что осталось непроверенным и почему, а также способ отката правки.
- Остановлена ли VM; применялись ли изменения к хосту.

```bash
bin/ui-vm stop
bin/ui-vm status
```

После остановки `status` показывает `qemu: null` и возвращает код **1**:
для этой команды это нормальный признак отсутствия работающей VM.

Задача с изменением поведения готова, когда текущая сборка загрузилась,
новая функция прошла свой сценарий, относящиеся к ней регрессии не появились,
а результат подтверждён наблюдениями. Если KVM, графика, сеть или устройство
недоступны, выполните доступные проверки и явно отметьте VM-проверку как
незавершённую с конкретной причиной. Не выдавайте успешный build за успешный
UI-тест. Для правок только документации без изменения поведения достаточно
проверки описанных команд и ссылок; загрузка VM не обязательна.

## Что покрывают готовые тесты

`smoke` проверяет готовность сессии, ошибки конфигурации Hyprland, открытие
нового окна Kitty через виртуальную клавиатуру, launcher с вводом `kitty`
и календарь AGS по клику на часы. Перед проверкой закройте открытые меню и
popup-окна. Он сохраняет скриншоты; оценка оформления
по этим изображениям выполняется отдельно человеком или агентом.

При 3D-рендеринге QEMU может отвечать `no surface` на `screendump`. Команда
автоматически использует `grim` внутри Wayland-сессии и получает PNG через SSH.
До запуска графической сессии этот способ ещё недоступен; для диагностики
остаются `serial.log` и Unix socket `serial.sock` (консоль гостя).

Модульные проверки транспорта управления:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p test_ui_vm.py -v
git diff --check
agent-check "$PWD"
```

Регрессионные проверки рабочего стола на запущенной VM:

```bash
python3 tests/desktop_vm.py
```

Проверяются отмена и сохранение скриншотов, исключительность и таймаут popup,
реакция CPU на нагрузку, отметка аудиовыхода, блокировка по таймеру hypridle
и сохранение экрана блокировки при перезапуске службы.
Тесты вводят данные виртуальной клавиатурой и мышью: во время запуска не
управляйте VM вручную. Используются стандартное разрешение 1280×800 и
таймаут AGS 30 секунд. Буфер обмена гостя меняется, в нём сохраняется PNG.
Два временных аудиовыхода удаляются после проверки.

Проверка применения темы на запущенной VM:

```bash
python3 tests/theme_vm.py
```

Она сверяет CSS браузера с текущей сборкой, активные темы терминальных
программ, акцент GTK и разбор конфигурации/разблокировку Hyprlock. Запускайте
её после первой загрузки на чистом диске и после переключения темы на том же
диске: так обнаруживается запаздывание оформления на одно поколение.
Проверка ожидает LibreWolf, пользователя `ui` и пароль VM `ui`.

Модульные проверки обновления браузерных профилей, включая сохранение
пользовательских настроек, истории и вкладок:

```bash
python3 -m unittest discover -s tests -p test_browser_theme.py -v
```

## Профиль для новой функции или темы

Временные настройки проверки храните вне репозитория. Следующий пример
включает Planify и Crimson поверх стандартного профиля, сохраняя тестового
пользователя, AGS, виртуальное оборудование и ограничения VM. Замените
переопределения на относящиеся к своей функции. Для некоторых приложений
нужен также флаг `features`, например `features.gaming` для Steam.

Инициализируйте `UI_VM_STATE` командой `bin/ui-vm paths`, как описано выше.
Из корня проекта создайте файл:

```bash
export UI_VM_REPO="$PWD"
cat > "$UI_VM_STATE/feature.nix" <<'NIX'
let
  root = builtins.toPath (builtins.getEnv "UI_VM_REPO");
  flake = builtins.getFlake ("path:" + toString root);
  lib = flake.inputs.nixpkgs.lib;
  base = import (root + "/vm/ui/test-vars.nix") { inherit lib; };
  vars = import (root + "/lib/merge-vars.nix") base {
    theme = "crimson";
    programs.planify = true;
  };
in
import (root + "/lib/mk-system.nix") {
  inputs = flake.inputs;
  system = "x86_64-linux";
  inherit vars;
  configDir = "/etc/ui-vm";
  configurationModule = root + "/vm/ui/configuration.nix";
}
NIX
```

Сборка и запуск этого профиля:

```bash
(
  set -e
  bin/ui-vm stop
  nix build --impure --no-write-lock-file \
    --out-link "$UI_VM_STATE/build" \
    --expr '(import (builtins.toPath (builtins.getEnv "UI_VM_STATE") + "/feature.nix")).config.system.build.vm' \
    > "$UI_VM_STATE/evidence/build.log" 2>&1
  bin/ui-vm start --no-build
  bin/ui-vm wait --timeout 180
  bin/ui-vm exec -- ui-session hyprctl dispatch exec io.github.alainm23.planify
)
```

`--impure` здесь нужен для путей из переменных окружения. Локальные vars и
оборудование основной системы этот пример не импортирует. `path:` включает
новые файлы проекта без добавления их в индекс Git. При продолжении в новом
терминале восстановите обе переменные: `UI_VM_STATE` и `UI_VM_REPO`.

**Для такого профиля не используйте обычный `bin/ui-vm build` или `start`
без `--no-build`: они заменят результат стандартной конфигурацией.**
При следующих изменениях повторяйте именно пользовательскую команду
`nix build`, затем `start --no-build`. Сохраните `feature.nix` вместе с
доказательствами, чтобы следующему участнику были известны параметры проверки.

Для проверки тем меняйте `theme` между `catppuccin`, `crimson` и
`catppuccin-mocha`, пересобирайте и загружайте VM на том же диске, затем
выполняйте `python3 tests/theme_vm.py`. Этот тест рассчитан на LibreWolf;
для Floorp задайте `browser = "floorp"` и отдельно проверьте его реальный
профиль, CSS и интерфейс. После смены CSS перезапускайте браузер.

Постоянный сценарий, нужный другим участникам, оформляйте как повторяемый
тест/профиль в `tests/` или `vm/`. Временное включение тяжёлого приложения
не должно случайно остаться в стандартном `vm/ui/test-vars.nix`.

## Диагностика неуспешной проверки

- Ошибка build: смотрите сохранённый `evidence/build.log`; проверяйте
  включение нужного модуля и конфликт опций до запуска VM.
- `wait` завершился по таймауту: проверьте `bin/ui-vm status`, затем
  `qemu.log` / `serial.log` и журнал Home Manager:
  `bin/ui-vm exec -- journalctl -b -u home-manager-ui --no-pager -n 80`.
  Готовность SSH ещё не означает готовность рабочего стола.
- Сбой интерфейса: снимите экран и прочитайте журналы именно приложения.
  Диалог первого запуска, экран входа или окно «не отвечает» не подтверждают
  работу сценария за этим диалогом. Отметьте границу фактической проверки.
- Нет сети: в VM включён `restrictNetwork`. Отделите локальную проверку
  от сценариев входа в аккаунт, скачивания плагинов и внешних API. Не считайте
  такой сценарий пройденным по заглушке или одному процессу.
- Проблема с GPU: virtio/virgl не воспроизводит NVIDIA. Zed может использовать
  программный Vulkan и показывать предупреждение; для проверки его оформления
  допустим разовый запуск в госте с `env ZED_ALLOW_EMULATED_GPU=1 zeditor`.
  Зафиксируйте этот режим; не переносите выводы о производительности на хост.
- `status` показывает неработающую VM, но SSH отвечает: проверьте, не остался
  ли другой стенд на порту 22222. Не продолжайте тест в неизвестной VM.

## Настройки, состояние и ограничения

- `vm/ui/test-vars.nix` задаёт тестовые переменные, включая тему. Локальные
  `/etc/nixos/vars.nix` и `hardware-configuration.nix` не импортируются.
- `vm/ui/configuration.nix` задаёт ресурсы и исключения VM. Необязательные
  тяжёлые приложения выключены, AGS включён, браузер — LibreWolf.
  Есть тестовые обои; диалог обновления Hyprland и ротация логов отключены.
  Hypridle запущен, но обычные таймеры затемнения, блокировки и сна заменены
  бездействующим обработчиком: стенд не засыпает во время длительных проверок.
- `bin/ui-vm paths` показывает каталог диска, SSH-ключа, сборки, логов
  `qemu.log` / `serial.log` и снимков. По умолчанию это отдельная папка в
  `~/.local/share/agent-workspaces/ui-vm/`, привязанная к пути репозитория.
- Можно задать `UI_VM_STATE` вне репозитория: короткий путь без пробелов и
  запятых, изначально пустую папку. Используйте одно значение для всех команд. Одновременно допускается
  одна команда управления этим каталогом. SSH использует порт `127.0.0.1:22222`;
  одновременно на одном хосте запускайте только один стенд.
- У пользователя `ui` пароль `ui` для консоли и sudo без пароля только в VM.
  SSH принимает только отдельный ключ стенда, парольный вход отключён.
  QMP и аварийная serial-консоль доступны через Unix sockets в каталоге стенда.
- Гостю доступны Nix store хоста только для чтения и служебные каталоги VM.
  Домашняя папка хоста и рабочий репозиторий не подключаются. Исходящие
  подключения гостя ограничены QEMU `restrictNetwork`; сценарии с Интернетом
  требуют осознанного изменения профиля.
- Используется виртуальная 3D-графика virtio/virgl, анимации и автоматическая блокировка
  выключены. Драйвер NVIDIA хоста в гостевую систему не переносится. Проверка
  плавности, NVIDIA, физических мониторов, Bluetooth и
  других устройств требует отдельного запуска на соответствующем оборудовании.
- Диск сохраняется между запусками. Для чистого состояния остановите VM и
  перенесите `disk.qcow2` и `known_hosts` из её каталога в резервную папку;
  следующий запуск создаст новый диск. Не удаляйте их у работающей VM.
- `stop` запрашивает штатное выключение через ACPI. При таймауте он сообщает
  об ошибке, не убивая посторонние процессы по устаревшему PID.

Если загрузка не удалась, сначала смотрите `qemu.log`, `serial.log` и снимок
экрана; успешная сборка Nix ещё не означает, что рабочий стол запустился.
